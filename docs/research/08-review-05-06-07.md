## 0. 一頁結論

1. **05 最重要的建議（每個測試從 template `CREATE`，結束就 `DROP DATABASE`，再平行）和 G21 實測結果衝突，照原樣做會讓 G21 更嚴重。**
   - PostgreSQL 18 的 `dropdb()` 會先刪 `pg_database` 那一列，再呼叫 `RequestCheckpoint(CHECKPOINT_IMMEDIATE | CHECKPOINT_FORCE | CHECKPOINT_WAIT)`，整段期間都持有 xid。
   - 實測中壓住 horizon 的 7 次快照全是別的 DB 的 `DROP DATABASE … WITH (FORCE)`，每次 18–70 秒。
   - 每個測試 DROP 一次，就是每個測試在整個 cluster 製造一次這種停頓。
   - 要改成「固定 N 個 slot DB 重複使用」，或者把 DROP 延到整套跑完、而且只在 `fsync=off` 的專用 cluster 上做。
2. **05 對 G21 根因的判斷（cluster 共用的 `pg_snapshot_xmin`）正確**，程式與實測都支持。但它列的嫌疑來源（開發伺服器、長交易測試）不是實測抓到的。它也漏了兩件事：
   - 測試套件本身就有 12 個檔會 `DROP DATABASE`（10 個 `m1_*_upgrade`、`s3_permissions`、`s5_changesets`）；
   - E2E 每次 reset 都 `DROP DATABASE`。
3. **有一個比 template 更簡單、也不碰 DROP 的作法被漏掉了：** 讓 `test_pool()` 依 slot 號碼選 `oxledger_test_<slot>`，沿用現有的 TRUNCATE reset。
   - `test_pool()` 原本就會自動建立不存在的 DB；
   - nextest 有 `NEXTEST_TEST_GLOBAL_SLOT`；不用 nextest 的話，也可以用行程內的號誌加 advisory lock。
4. **06 的現況描述大致正確。**
   - request id 對不上、沒有任何 span、`RELEASED_IN_TRANSACTION` 沒匯出、`/healthz` 是靜態 `ok`，都已核實。
   - 有兩處錯誤：MCP 的領域錯誤其實會用同一個 request id 寫 log；E2E 沒有設定 metrics token。
   - G35 一段應改寫：G35 和 G20 同根因，已在 `0f7c7fd` 修好。
5. **07 的數字抽查全部正確**（`search_with` 673 行、`commands.rs` 5,274 行、`query!` 0、`unsafe` 0、48 個 commit）。
   - 主要問題是低估了 `cargo-mutants` 的成本。測試全套要 20–30 分鐘，而且共用同一個 DB，mutants 只能單工跑，所以必須先做完 05。
   - 「被 feature 靜默略過的測試」漏了 3 個 `ai` 測試檔。
6. **工具維護者所在地：沒有發現違反「不用中國產品」的情況。** Vitest／Vite 的部分見 §4.1：VoidZero 已在 2026-06-04 被 Cloudflare（美國）收購，05 的 A6 應該補上這個事實。

## 1. 05 template DB＋平行，和 G21 實測相容嗎？

### 1.1 實測（協調者轉述的後端 session 結果）

- `sync_all`／`dispatch_all` 只處理 xid 比 cluster 共用的 `pg_snapshot_xmin` 還舊的 outbox 列。
- 逾時當下拍了 7 次快照，壓住 horizon 的都是別的資料庫正在跑 `DROP DATABASE … WITH (FORCE)`：6 次是 E2E 在重建 `oxledger_fe_e2e`，1 次是升級測試建的暫時 DB。
- DROP 會等 immediate checkpoint。這台機器每次要 sync 約 2 萬個檔，花 18–70 秒。
- 排除 `after_release`：開和關交替各跑一輪，逾時次數 5 比 4。

### 1.2 原始碼核對

- PostgreSQL `REL_18_STABLE` 的 `src/backend/commands/dbcommands.c`，`dropdb()` 內的順序是：
  1. `CatalogTupleDelete`
  2. `ForgetDatabaseSyncRequests`
  3. `RequestCheckpoint(CHECKPOINT_IMMEDIATE | CHECKPOINT_FORCE | CHECKPOINT_WAIT)`
  4. `remove_dbtablespaces`

  第 1 步改了 catalog，所以已經分配 xid；第 3 步要等 checkpoint 做完。這和實測完全吻合。
- 同一個檔案的 `createdb()` 只在 `FILE_COPY` 策略下做 checkpoint，預設的 `WAL_LOG` 不做。所以 **CREATE 本身問題不大，問題在 DROP**。
- oxledger 的 `sync_all`（`crates/oxledger/src/search.rs:1580`）完成條件是 `c >= want || want.xid < f`。
  - 只有 xid 比目標 outbox 列還舊、而且還沒結束的交易會卡住它。
  - 短交易很快就結束；持有 xid 18–70 秒的 DROP 剛好就是會讓 20 秒上限逾時的那一種。

### 1.3 結論：原方案不相容，修正後可以相容

| 作法 | 每個測試的 DROP | 對 G21 | 評估 |
|---|---|---|---|
| 05 §4.1 原案：每個測試 `CREATE … TEMPLATE`，通過就 `DROP … WITH (FORCE)` | 400 次左右 | 平行時任何時刻都可能有 DROP 在等 checkpoint，同時在跑的測試 `sync_all` 會大量逾時。DB 越多，要 sync 的檔案也越多 | **不可行**（在共用的 `oxledger-pg` 上尤其糟） |
| 原案＋專用測試 cluster（`fsync=off`，tmpfs） | 400 次左右 | checkpoint 不做 fsync、寫的是 RAM，每次停頓預期降到毫秒到百毫秒，但仍是 cluster 層級的停頓 | 可行，但要實測；風險還在 |
| 每個測試從 template CREATE，**DROP 延到整套跑完**（或下次啟動時清） | 0（跑測試期間） | 跑測試期間沒有 DROP；結束時一次清掉 | 可行；只是跑測試期間 DB 數量會長到 400 個左右，checkpoint 檔案數也跟著漲（後端選項 3 的問題） |
| **固定 N 個 slot DB 重複使用**（`oxledger_test_0..N-1`，沿用 TRUNCATE reset） | 0 | 不會新增 DROP；也不會累積 DB | **建議**：改動最小，和現有的 reset 相容 |
| slot DB＋reset 改成從 template 複製 | 每次 reset 都要 DROP | 又回到 DROP 的問題 | 不建議 |

TRUNCATE 也會換新 relfilenode，等於建立檔案、刪除檔案，會增加 checkpoint 的工作量，但它不會像 DROP 那樣持有 xid 等 checkpoint。要知道它和 `DELETE` 哪個快（小表通常 `DELETE` 比較快），得量 A1 才知道。

### 1.4 對 05 其他段落的影響

- **§2.5 的嫌疑來源要改寫。** 實測抓到的是 DROP DATABASE；05 列的開發伺服器、`gate.reached` 長交易測試都沒抓到。測試套件本身有 12 個檔會 DROP DATABASE，在平行之下，同一套測試就會互相卡住。
- **§4.4-1「逾時時印出是誰」可以直接重用現有程式。** `metrics::xid_holders()`（`crates/oxledger/src/metrics.rs:358`）已經查 `pg_stat_activity` 裡 `backend_xid IS NOT NULL` 的 datname、application_name、query，以及 prepared transactions。05 寫成要另外寫一份。
- **F2（E2E 改從 template 建 DB）仍要 DROP 舊的 `oxledger_fe_e2e`**，就是實測裡 6 次停頓的來源。應該改用後端提出的選項 2：用 TRUNCATE 或重建 schema 來重置。
- **T4（專用測試 cluster）和後端選項 1（不同工作線用不同 PG 容器）方向一致**，應該合成一題。
