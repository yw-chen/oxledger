結論

G21 根因

sync worker 的前進界線 H＝pg_snapshot_xmin，是整個 cluster 共用的。實測抓到的是別的資料庫的 DROP DATABASE：等 checkpoint 18–70 秒，期間持有 xid，H 卡住，sync_all 20 秒逾時。

測試平行化

05 原案「每個測試從 template CREATE、結束 DROP」會把 G21 放大，不採用。改成固定 N 個 slot DB 重複使用（oxledger_test_<slot>），沿用 TRUNCATE reset，跑測試期間不 DROP。

可觀測性

有文字 log 與部分 /metrics；沒有 span、沒有 HTTP 與連線池指標，request id 和 log 對不上，/healthz 是靜態 ok。M2 的最小集合共 7 項，除了 json feature 外不加 crate。

程式品質

unsafe 0、TS any 0，測試比產品約 1:1。風險集中在少數超大函式與模組；SQL 全是執行期字串、沒有覆蓋率；mutation 驗證靠人工。數量型指標用棘輪管理。

決定

D1–D14 全部照 08 的建議。D5 第一批工具（cargo-nextest、cargo-deny、tracing-subscriber 的 json feature）已核准安裝。

可觀測性

現況盤點

Logs

tracing 文字格式寫 stderr，RUST_LOG 預設 info；json feature 沒開。全 repo 0 個 span；約 62 處事件，多半是 worker 的 warn!。沒有 access log。sqlx 慢語句（≥1 秒）、慢 acquire（≥2 秒）用 WARN 記。

Metrics

手寫 Prometheus 格式的 /metrics（要 token）：搜尋同步、notify、pg_oldest_xid_holder_age_seconds。缺：HTTP RED、連線池、GitHub／AI／field job／sweeper 的 worker 指標；RELEASED_IN_TRANSACTION 存在但沒匯出。

Traces／correlation

meta.request_id 每次回應新產一個 UUID，和 log 對不上；沒有 X-Request-Id，不接受 traceparent。池沒設 application_name，xid_holders() 的 application 欄是空的。

Health

/healthz 是 get(|| async { "ok" })，不碰 DB；沒有 readiness。E2E 的後端 log 是 warn、stdout: 'ignore'，不存檔。

做得好的地方

稽核在 DB 的 append-only 事件表、有 redaction，不走 tracing。hidden_content_stays_out_of_logs_and_audit（E4w-7）是新增 log 欄位時的守門測試。

08 對 06 的修正：(1) 「只有 500 會把 id 寫進 log」只適用 REST；MCP 的領域錯誤與 internal error 都會用和回應相同的 request_id 寫 log（mcp.rs:98-99、114-115）。(2) G35 是前端分支的編號，指連線池借出還在交易中的連線，導致 CREATE INDEX CONCURRENTLY 失敗；和 G20 同根因，已在 0f7c7fd 修好。可觀測性的作用改成偵測復發。(3) 痛點表要加 G21；application_name 優先度往前排，因為同時服務 G21 診斷。(4) E2E 沒有設 OXLEDGER_METRICS_TOKEN，要在 backend.mjs 加一個測試用 token。

M2 最小集合（7 項，依回報／成本排序）

  1. request id＋request span（I-1）：同一個 id 出現在 X-Request-Id 標頭、meta／error 本文、這個請求的每一行 log；route 用樣板（MatchedPath），不記 query string；/mcp 也套。
  2. 連線池指標＋application_name＋匯出 G20 計數（I-4）：db_pool_connections{state}、db_pool_acquire_seconds、db_pool_released_in_transaction_total；慢 acquire 門檻調到 500 ms。
  3. HTTP RED 指標（I-3）：http_requests_total{route,method,status_class}、http_request_duration_seconds{route}。
  4. worker 統一指標＋每輪 span（I-5）：rounds、last success、backlog、oldest pending age；先補 GitHub 與 AI（目前全盲）。
  5. E2E／測試失敗附件（I-7）：後端 log 存檔、失敗時附 log 片段＋/metrics＋worker 狀態。D11 決定提前做，因為直接幫助 G21 與 E2E 除錯。
  6. /readyz（I-6）：只看 DB 與 migration；worker 停滯用告警處理，不算 not ready。
  7. JSON log 開關（I-2）：開 tracing-subscriber 的 json feature（D5 第一批已核准）。

每一步都擴充 E4w-7 守門測試：也走一次 HTTP 層（含 ?q=秘密 的搜尋），斷言 span 與 JSON log 都不含秘密。估計後端 600–1,000 行（含測試）、前端／E2E 100–200 行。之後再做：Prometheus＋Grafana 告警、前端自產 traceparent、OTel traces（Rust traces 仍是 Beta）＋自架 Jaeger v2。
