02情境：傳統 vs AI 原生

每個情境都附上沒有 AI 時的退路。點選切換情境。

傳統
  1. 選專案 → 選 tracker
  2. 開表單，自己填所有欄位
  3. 送出；重複的單事後才被發現
AI 原生
  1. 在意圖列貼描述（第一切片只收文字）
  2. AI 分成「明說的事實／待確認／建議欄位」，沒把握的欄位留白
  3. 送出前搜尋可見範圍，「可能重複 AUTH-88」並排比較
  4. 產生 ChangeSet → 預覽 → 建立，或補充到既有單，或存草稿
不能做的事：把「昨天開始」寫成「確認是部署造成的回歸」；把私有內容複製到公開描述。
意圖列變成「開新 issue」捷徑，加上純 BM25 找相似單
傳統
  1. 打開「未分派」列表
  2. 一張一張點開
  3. 分類、指派、改優先
AI 原生
  1. 分流工作台是一張表：建議變更／根據／待確認
  2. 先套確定性規則，規則處理不了的才請模型；建議預設收合
  3. 逐筆、逐欄接受，或批次套用；套用前看完整 diff
  4. 套用後的回執分成功／失敗／衝突
可能重複 ≠ 關閉為重複。AI 提的 priority 不預先顯示成正式值；資料更新後，建議標成「需重算」。第一切片只做單筆。
同一張表，建議欄只剩規則結果
傳統
  1. 關鍵字 + 篩選
  2. 開一堆分頁自己比對
AI 原生
  1. 問句，AI 解析成的條件攤開給人看，可以直接改
  2. 三層結果：直接命中（命中欄位）、關係延伸（經過哪條 edge）、附來源的結論
  3. 可以轉存成 ViewDef；一次性的探索不進 DB
「沒找到」要說成「在目前可見範圍和這些條件下沒找到」，不能把 BM25 說成找齊了所有資料。
意圖列就是 BM25 搜尋，加上結構化語法
傳統
  1. 篩選 backlog
  2. 心算容量與相依
  3. 拖進 sprint 就生效
AI 原生
  1. 「先完成 SSO，留兩成給維運」
  2. 先檢查資料夠不夠；不夠就只說「整理候選範圍」
  3. 規劃模式：固定橫幅；提案卡用紫色虛線框並寫明新增或移出；沒估點的卡另外列，不當 0 點
  4. 2–3 個方案分頁比較，最後收成一個 ChangeSet
前提：sprint 的資料模型還沒定（Q5）。
規劃模式照常可以手動用
傳統
  1. 每人回想昨天、今天、阻礙
  2. 會後再補更新 issue
AI 原生
  1. 個人看到「待確認的站會更新」草稿（只放已記錄的變動）
  2. 「今天預計」由本人填，或沿用上次確認的計畫
  3. 團隊畫面只看新增阻礙、要別人決定的事、有風險的承諾
刻意不做依人輪播、自動代人發言、活動量評比。沒有事件不代表沒有工作。私人筆記不進團隊摘要。
用事件產生的確定性摘要，本人點開時才請模型潤飾
傳統
  1. dashboard 紅黃綠、burndown
  2. 自己解讀，再去找人
AI 原生
  1. 風險工作視圖，每一項都有：觀察／判定方式／證據／未知／建議行動
  2. 建議行動一鍵變成待確認的 ChangeSet
  3. 訂閱信在寄出時依收件人重新檢查權限
「已逾期」是事實，「可能延誤」是判斷，兩者樣式不同，並顯示資料更新時間。
規則產生的異常清單照常運作
傳統
  1. 逐頁設定欄位、角色、轉移矩陣
  2. 存檔就生效，影響靠自己推想
AI 原生
  1. 「Bug 進待驗證前必須有修正版本，只有 QA 能轉成已驗證」
  2. 產出三份：設定草稿 diff／影響報告／角色 × 狀態測試案例
  3. 先模擬，再發布版本

04視覺語言：波紋有固定意思

波紋代表看得見的資料流和影響範圍，不代表模型在思考，也不代表內容正確。下面兩個示範可以按按看。

八條規則

色彩各有固定語意

同一個藍色不能同時代表選取、AI 建議和成功。深色底 #0B1220，淺色主題沿用同一套語意。

來源讀取波紋

只在 server 回報開始擷取時，外擴一圈 350–500ms，完成後變成靜態勾選加時間。不可見的來源不顯示節點，也不顯示數量。

影響範圍：先靜態，回執後才動

預覽時加細框、關係線強調 150–200ms；收到成功回執後才播一次 250–350ms 波紋。部分成功時只標成功的項目。

等待和進度分開

有階段就更新階段名稱；只是在等就顯示已等待秒數。不用持續的波紋假裝有進度。

閱讀區禁止持續動畫

描述、note、diff、列表、權限設定、看板都不動。科技感靠排版、細框線、等寬數字。

規劃模式不只靠透明度

紫色虛線框加文字標記，再加固定橫幅；拖曳 120–180ms，不用大幅彈跳。

不跨權限、不暗示因果

只有實際產生事件的項目會亮；相關但沒被修改的項目用靜態標記。

無障礙是同一套設計

prefers-reduced-motion 時改成靜態框加文字；狀態附文字；焦點和提案的樣式不同；對比 ≥ 4.5:1。

05失敗情境：偵測 → 呈現 → 退路

情境偵測介面呈現系統退路
AI 誤判和明確脈絡比對、看有沒有反證、記錄更正與駁回、事後抽樣（schema 抓不到）欄位標「AI 建議」並附依據〔改選〕；可能重複用並排比較〔不是重複〕任何一欄都能改；駁回只對這次有效；已套用的就產生補償提案；沒確認的 duplicate 不會關單
幻覺引用只能用這次檢索回傳的來源 ID；resolve／describe 驗值；dry run 和 apply 各驗一次「這個來源目前無法驗證」，不產生假卡片；不合法的值旁列出合法選項不合法的操作不能執行；重新組成提案；重試有上限；不存在和沒權限顯示同一種訊息
權限洩漏摘要、facet、ChangeSet、通知、快取、提示注入，6 個出口各自檢查（見下方說明）「部分內容目前無法顯示」，不露出標題或數量；「內容使用了受限來源」重建或隱藏；改存成私人草稿；讀不到完整範圍就不能核准
沒有 AItimeout、熔斷；能力開關；斷線；隔離網路設定小條「AI 暫時無法使用；資料與操作正常」；關閉時直接隱藏；斷線時標快取時間意圖列退化成搜尋加指令；不排隊寫入，重連後也不自動送出
成本與延遲開始前估算筆數和輸入量；追蹤 token、工具次數、時間〔先分析選取的 20 筆〕〔背景分析全部〕；顯示真實階段；AI run 的取消只停後續的模型與工具呼叫；已開始的 apply 只顯示「結果確認中」確定性摘要優先、增量重算；任務、個人、組織三層預算；不偷偷換供應商
不信任／盲從開了預覽就放棄、套用後馬上更正、高影響操作一律全選（只當設計訊號）「只會改這三個欄位」；可以只套用一欄；高影響項目不預設全選；不用倒數催人可按專案關閉 AI 建議；品質異常時降級成只提案；不追求最大接受率
權限洩漏的已知限制：外部 agent 一旦讀到明文，oxledger 無法保證它不在外部外洩。所以委派政策要把「可以讀 private」和「可以公開發布」分開。

06AI 放在哪裡

核心不依賴模型

AI 執行層可以關掉；外部 agent 透過 MCP 使用同一套能力。

共用 registry 的代價

新工具預設不對所有入口開放；approve_changeset 永遠不交給模型；契約要有版本；E5 要分兩條線量。

BYOK 不是隱私架構

預設由管理員核准供應商和資料出口；個人 key 不能繞過組織政策。

07c規格重點（第 6–7 輪收斂）

把之前留著沒定的細節收成可以實作、可以測試的規格。完整內容見 md §15；產品方向仍留給使用者。

第一切片

單一目標 · atomic · 人核准並套用

每個版本只動一張 issue（或建立一張）；另外開放單一的 duplicate_of。同一版本最多成功套用一次。agent 和內建模型都不能核准或套用，handler 自己拒絕，不只靠隱藏工具。

核准

綁 version + proposal_hash

只改 title 或 evidence 也要重新核准。「核准並套用」是一個按鈕，但 approval 和 execution 是兩筆紀錄，不放在同一個交易。

執行資格

六個條件全部成立

執行者有權、核准有效、授權來源沒撤銷、在提案者原本的上限內、委派者仍有權、每一項權限都通過。人按套用不會放大 agent 的提案範圍。

錯誤

細節先過可見性

not_found 對「不存在」和「看不到」形狀一樣；conflict.current、allowed、legal_values 只回可以揭露的部分。

互動規格

主題規格
⌘K 路由組字中不送出 → 整段 issue key 直接開單 → 整段結構化語法就查詢（語法錯誤標位置，不改送模型）→ slash 指令開預填表單 → 其他自然語言按 Enter 才送模型；超過 500 字或有換行先給三個選項。回傳 route_kind 方便測試
「需要你決定」只由規則、ChangeSet 狀態、待回覆事件產生；去重鍵 (recipient, rule, subject, reason)；條件解除就自動結案；失去權限時立即消失；首頁 10 筆
AI 建議過期第一版自動重新驗證，重新產生建議要人按鈕；來源更新就標黃色；已核准的提案絕不在背景被改
衝突審閱三欄：原始值／目前值／原提案結果，逐欄選擇；按鈕是「建立修正版提案」，不是強制覆蓋
validate 呈現寫「目前檢查通過」，附檢查時間；五類檢查分開顯示；逾時顯示「結果確認中」

07d執行與工作脈絡（第 8 輪收斂）

任務、AI 執行層、ViewDef／session、評估的規格。數值是建議的初始值；完整內容見 md §16。

任務

task 和 run 分開

task 只有 active／done／abandoned；每次 AI 執行是一筆 run。task 只關聯 ChangeSet，不擁有它的生命週期。打得開任務 ≠ 讀得到它引用的來源。

AI 執行層

預算先保留，熔斷分端點

每個 run 最多 12 次工具呼叫、60 秒；單次模型請求 30 秒。熔斷只算 timeout／網路／5xx，打開 60 秒後半開放 1 個探測。

提示注入

結構性防線，不靠模型自律

身分不可偽造、每次呼叫重新授權、來源標籤由 server 維護、讀過受限資料就保守繼承限制、寫到更大受眾時檢查、不能自己解除限制。

ViewDef／session

能力由 server 算

文件只能寫 requested_features；不做 deep merge；ACL 強制 AND。session 閒置 30 分鐘、最長 8 小時，每主體 20 個，不存 access token。

結果意思介面
ai_unavailable服務無法啟動：停用、熔斷打開、沒有核准的端點「AI 暫時無法使用；資料與操作正常」
quota_exceeded開始前就知道額度不足說明額度用完，不寫成故障
stop_reason=budget_exhausted執行中途用完預算保留部分結果（已驗證來源／未驗證文字／ChangeSet），標明沒做完
評估門檻（E5）標準
越權、未核准套用、重複效果0 · 阻擋發布
洩漏定義好的 canary 和路徑上 0 次；只能說「受測案例零失敗」，不是安全證明
核心情境正確率每個核心情境 ≥ 90%；每案例至少跑 3 次，固定 agent／模型／prompt 版本
CI 分層每個 PR 跑確定性測試 → 契約／prompt／模型變更時跑 live E5 → 每晚完整 → 發布前加人工抽查
