0三種保證，分開講

這三件事常被當成同一件事。這份設計只提供前兩種。

提供

引用可驗證

這段文字現在確實在呼叫者讀得到的來源裡。不證明「伺服器曾經回傳過」，也不證明「歷史上存在過」。

提供

搜尋追上寫入

對寫入交易 X，這次搜尋的 reader 已經套用所有 xid ≤ X、且有登記在 outbox 的事件。

不提供

跨系統同一時間點

tantivy 和 PostgreSQL 不在同一個快照裡。最後一律回 SQL 複驗，所以結果只會少、不會多。

2MCP 主要用法與呼叫序列

以外部 agent 為第一使用者，由這 5 個用法反推 API。token 數是粗估，還沒用實際的 tokenizer 量。

  2. （人在 SPA 核准並套用，不經 MCP）

通則

從用法反推的設計

brief 是預設，每筆 1 段約 60 字並附 citation。fields 可選。錯誤格式同 02 §4.3：頂層 retry_after_ms、next_actions（6 種封閉列舉），details 帶 path、suggested_tool。agent 不碰 offset。search_lagging 不是寫入失敗；complete:false 時不能回答「不存在」。

讀取範圍

agent＝委派讀取範圍

agent 憑證呼叫 search、get、get(citations)、verify_citations、get_source 時，範圍是 02 §3.5 的委派範圍：工作脈絡內所有有效委派專案的聯集（U1 已決定可多專案），每個專案都排除私有 issue、私有 note、visible=false 欄位；搜尋可能跨多個專案。手工構造的 citation 也只會得到 not_found；issue_note 一定同時比對 note.issue_id。委派失效時整批回 delegation_unavailable；脈絡停用（曾授予的任一專案改了權限設定）時整批回 context_unavailable；都不降成逐筆 not_found。

查「登入」· primary
從公司入口登入後又被導回登入頁

「入口」的「入」不亮：欄位裡已經有 primary 命中時，0.1 權重的 unigram 不亮。

查「付不了錢」· fallback
按下付款後顯示錯誤，錢沒有扣到

只有低權重的字元命中：用淡色，並標「部分字元相符」，不宣稱原文有「付不了錢」。

登入失敗時顯示 invalid_grant

「登入」「入失」「失敗」三個 bigram 的範圍取聯集，不重複輸出字元。識別碼整串命中時亮整串。

4寫入後的搜尋一致性

token 只放寫入交易自己的 xid8。reader 帶一個排他 frontier F，X < F 就代表追上了。

寫入回執（02 §6.9）

{status:"succeeded", effects:[{issue_id, key:"AUTH-124", lock_version:0, changed:true}], search:{consistent_after:"c1.<epoch>.<xid8>"}}。人看 /commands 回應，agent 看 changeset_get 的 execution。epoch 和 xid 在寫入交易裡一起存成完整 token，重播回原 token。token 不簽章，也不能證明 commit。epoch 輪替以 search_settings 那一列為協調點：寫入交易加 FOR SHARE，輪替交易提交後才切換索引，不必停寫入。

search 參數

consistent_after、wait_ms（0–2000，預設 1000）、on_lag: return|error。純 SQL 查詢回 not_applicable。〔on_lag 預設待確認 Q-S4〕

逾時

outcome:"search_lagging"、complete:false、items:[]、沒有 cursor。不回舊結果，免得 agent 把它當成「不存在」。

長交易會不會擋住 frontier（PG 18.6 實測）

開啟中的交易擋 frontier
別的 database，唯讀快照（沒有 xid）不擋
別的 database，已分配 xid擋
同一個 database，唯讀快照不擋
同一個 database，已分配 xid擋
CREATE INDEX CONCURRENTLY，1,770 萬列，18 秒不擋（backend_xid 一直是空的）
單一 UPDATE 改 95 萬列，35.3 秒擋 35 秒

告警看的是整個 instance 裡 backend_xid IS NOT NULL 的最老交易：超過 15 秒 warning、60 秒 critical。不自動 kill。大量更新一律分批。

5D14 效能尾巴（100 萬 issue、1,770 萬列 issue_cf）

單一條件的估計誤差（低估倍數）

多條件 + ORDER BY id DESC LIMIT 50：S0 現行 vs S2 逐列探測（ms，對數刻度）

策略

只用在「無 q、id DESC、LIMIT ≤ 100、≥ 2 個單值欄位正向條件的 AND」。每個條件做上限 10,001 的索引探測（0.5–11 ms）：任何一個 ≤ 10,000 就用 S0，全部 > 10,000 就用 S2。

deadline

預設 2 秒，涵蓋探測、初始策略和最多一次切換。用剩餘預算設 statement_timeout；用完回 query_timeout，不回部分頁。

總數

count(*) 要 197–497 ms：第一版不回總數，只顯示「還有更多」。〔Q-S6〕

改型別（就地分批，數字 → 文字）

動作數量耗時
分批轉換（每批約 1 萬個值，各自 COMMIT）798,071 值 / 80 批13.1 s（最慢一批 0.43 s）
CREATE INDEX CONCURRENTLY 新的 per-field index—9.1 s
對照：單一 UPDATE949,336 值35.3 s（整段擋住 frontier）

不含觸發器成本，是本次環境的參考值。維護期間這個欄位不能讀、寫、篩選，get 回 value_available:false，不回 null。要不要支援就地改型別：〔Q-S9，建議預設：不支援，改用「建新欄位 + 複製轉換」〕

6使用者方便性檢查表

UX-1

為什麼命中

顯示命中的欄位名稱和約 60 字的片段，命中的詞高亮（不只靠顏色）。部分字元命中標「部分字元相符」。純欄位篩選列出欄位值。

UX-4

剛建立的單

回執一回來就顯示「已建立 AUTH-124」；搜尋清單上方另外放「剛建立・搜尋同步中」卡片，可以開啟、引用。不能只因為搜尋延遲就顯示失敗。

UX-6

欄位篩選慢

400 ms 後顯示「正在套用欄位條件…」和「取消」。到 deadline 時給一鍵縮小範圍的建議，不偷偷改條件。

UX-8

結果不完整

truncated 或 complete:false 時要說「結果可能不完整」，不能只顯示一個空列表。不顯示會誤導的總數。

UX-9

引用失效

回 source_changed 時顯示「原文已修改」和「查看目前內容」，不靜默刪掉引用。

UX-10

欄位維護中

篩選器上標「維護中」，值顯示「暫時無法顯示」，不顯示空白。

7實作順序

步內容完成標準（摘要）
1spanned lexer，tokenizer 補 offset（索引格式不變）E1 語料全文的 term 序列和舊版相同；offset 屬性測試通過
2evidence、explain、fields、拿掉 score、原文比對淘汰CJK、識別碼、Unicode、預算測試；E1 的 nDCG 不變
3citation_id（含 issue_note）、verify_citations、get_source、get(citations)；委派讀取範圍；next_actions「找不到」和「沒權限」的回應位元組相同；agent 對私有內容一律 not_found
4同步迴圈：H 和事件同一個 statement、SearchView + F、payloadfrontier、重啟、kill -9 測試
5–6consistent_after／wait_ms／on_lag；回執帶完整 token（02 §6.9）用法 D 的 E2E（提案 → 核准 → changeset_get → get）；epoch 輪替後回原 token；agent 不重送提案
7–9指標與告警、藍綠重建、search_rev重建期間搜尋不中斷；跨 database 的長交易會觸發告警
10–11D14 策略選擇；resolve(custom_field)選對策略、相對改善；毫秒數只當參考
12E6依結果調整 wait_ms 和告警閾值
13–14改型別；受限內容進索引Q-S1、Q-S9 已定；受限內容進索引等 Q-S2
