03核准並套用時序

核准和執行請求同一個短交易：執行失敗時「曾經核准」不會消失，也不會只有核准、請求卻遺失。

04鎖的固定順序

所有寫入入口、撤銷入口都遵守；管理交易改安全設定時，先依序鎖受影響專案，trigger 只是防漏。

圖中省略的協調列：executions 之後是 agent_work_contexts（propose／revise／套用 SHARE，建立委派、關閉脈絡 UPDATE）；agent_clients 之後是單列 project_catalog（全專案 epoch 更新 UPDATE、建立專案 SHARE，第 20 輪）；agent 提案的 projects 是「R ∪ 目的地」依 UUID 排序。管理交易：principal 類先鎖 principal、群組類先鎖群組 principal（第 19 輪），之後才算受影響專案並鎖 projects；epoch 更新不鎖脈絡。

已在 PG18 實測：持有 FOR SHARE 時另一交易 UPDATE 同列會等待（lock_timeout 逾時失敗）；兩個 FOR SHARE 可並存。

05受眾一致專案與 security_epoch

Q4 關閉：server 要能證明 agent 寫的地方，受眾不會比它讀的地方大。

定義

受眾一致專案

每個給出 view_issues 的有效角色：issues_visibility ∈ {all, default} 且 view_issues 不限 tracker。這時所有非私有 issue／note／visible 欄位對同一組人可見。

反例（第 2 輪）

同專案也可能擴大

角色是 own 時，Alice 的單與 Bob 的單可讀的人不同；agent 從 A 抄到 B 就擴大受眾。所以第一版拒絕這類專案。

反例（第 3 輪）

跨時間

agent 讀到欄位 7 → 欄位 7 改成受限 → agent 寫進 note。只重算「是否一致」擋不住，所以加 epoch。

反例（第 4、5 輪）

跨委派、遮蔽後重提

兩份委派 P 讀 Q 寫；遮蔽後用原委派重提原文。遮蔽也 bump epoch；P 讀 Q 寫在 U1 改成多專案後由下面的工作脈絡規則處理。

多專案（第 14–17 輪）

工作脈絡與曾授予集合 R

R＝脈絡曾授予的專案，撤銷、到期、換 token 都不移除。每個提案版本存下當時的 R 快照；寫入目的地的讀者 ⊆ 快照中每個專案的受眾（比使用者集合＋匿名，不比人數）。私有目的地算實際讀者。owner 修訂不能洗掉來源。

脈絡失效

任一專案設定變，整個停用

R 中任一專案 epoch 改變 → context_unavailable，包括只涉及其他專案的提案。要恢復只能由人在 SPA 建新工作脈絡（step-up＋宣告）；server 無法驗證 agent 真的忘了舊內容（U14）。

值得多這一步

每份都要人核准（agent 可能被提示注入）；長文、note、建立、duplicate 不能用佇列勾選；發 token 要 step-up；建新工作脈絡要宣告；衝突由人選值。

移除的摩擦

「下個版本」怎麼解析

agent 寫里程碑（§17.9a）

命令

create_version／update_version

經 command_submit，單獨一份文件、一個 op；修改要帶里程碑的 lock_version。不能設 sharing、不能刪除。

權限與受眾

委派者要有 manage_versions

名稱、描述是專案的公開內容，照「公開目的地」受眾規則檢查；來源受眾比較窄就擋。

鎖

只共用 projects → versions

直接寫入、送審套用、人工回復各自沿用原本的前段；里程碑文件從不鎖 issue，所以和排入 issue 沒有環。人工回復不看 agent 的委派與配額。

配額與回復

每小時建 10 個

同一里程碑 10 分鐘改超過 5 次觸發熔斷。逐欄回復只動「目前仍是那次寫的」欄位；回復建立＝軟刪除，有你看得到的單在裡面就不行。

健康度（讀取時算、只用你看得到的單）

狀態條件（由上往下第一個成立）
closed里程碑已關閉
no_date沒有日期
overdue日期已過、還有未結案的單
